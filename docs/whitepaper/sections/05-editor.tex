\section{The editor}
\label{sec:editor}

A config is a good thing to run and a poor thing to guess at. Choosing a
threshold, a kernel size or a flow gain is not a design decision that can be
reasoned out in advance; it is a matter of moving a number and looking at the
frame. The editor exists for that, and for nothing else: it authors the same
YAML the CLI runs, with a live preview of every stage and every sink.

\begin{figure}[t]
  \centering
  \includegraphics[width=\textwidth]{figures/editor-window.png}
  \caption{The editor on the \texttt{motion} recipe: stage list, the parameter
    form generated from \texttt{farneback}'s constructor signature, the live
    preview at frame 400, and the per-frame metrics beneath it.}
  \label{fig:editor}
\end{figure}

Nothing in Figure~\ref{fig:editor} is hardcoded. The palette lists what the
registry holds; the form is generated by reading the selected stage's constructor
signature, so a parameter's name, type and default reach the screen from the same
declaration the CLI builds from. Adding an operator to the codebase adds it to
the palette, with a working form, without touching the editor --- and it is not
possible to ship a stage the editor cannot show, or a form field the pipeline
ignores, because there is only one declaration to disagree with.

Three parts of the window earn their place beyond that:

\paragraph{The preview tabs are the taps.} Every named stage and every sink
becomes a tab, so the frame the encoder will write, the mid-chain mask and the
untouched source are one click apart. Most of the work of tuning a chain is
deciding \emph{which} intermediate image is wrong, and that is a question about
the middle of the chain, not its end.

\paragraph{The metrics update with the frame.} \texttt{motion\_px},
\texttt{motion\_objects} and the rest are computed by the same stages that would
compute them in a batch, so the number under the preview is the number the JSON
sink would write. Tuning against a picture alone is how a chain ends up tuned to
one frame.

\paragraph{The transport is a seek, not a play button.} A background model that
has seen sixty frames behaves differently from one that has seen four, so the
preview walks frames in order and the scrubber tells the worker where to be.
Frame~400 of 899 in the figure is not a decoded still; it is the state that chain
is in after four hundred frames.

The output is a plain YAML file. There is no project format, no editor-only
field, and nothing that has to be exported before a batch can run it --- the file
in the editor \emph{is} the file the CLI takes. For operators who should not have
to install a Python toolchain to get this far, the editor also ships as a
one-file AppImage and a dmg, built from the same source by the release workflow
on every tagged version.
